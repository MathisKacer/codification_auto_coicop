Troncature niveau 4 : le fix cascade des “0” terminaux

Pourquoi retirer les “0” finaux ne fausse aucune mesure d’accuracy du site

Published

August 17, 2026

Ce fix n’est pas propre à un classifieur ou à une analyse en particulier : il est implémenté dans tronquer_niveau(), la fonction de troncature utilisée par toutes les pages de ce site (src/coicop.py::tronquer_niveau côté Python, logique identique côté R pour les analyses SIRUS). Toute mesure d’accuracy au niveau 4 affichée ici — fiabilité des classifieurs, profondeur des codes, modélisation — en dépend. Cette page démontre que ce fix est légitime, une fois pour toutes, plutôt que de le supposer dans chaque analyse qui l’utilise.

Constat de départ : la troncature au niveau 4 garde 5 chiffres significatifs d’un code COICOP. Deux codes qui ne différaient que par un “0” terminal ("01.1.1.0" vs "01.1.1") étaient comptés comme des catégories différentes par simple comparaison de chaînes, alors que ce “0” est un artefact de troncature (“pas de subdivision à ce niveau”), pas une vraie sous-catégorie. Fix : retrait en cascade des “0” terminaux, à n’importe quel niveau de la hiérarchie.

Question posée : après ce fix, l’accuracy mesurée augmente fortement — est-ce légitime, ou le fix fusionne-t-il à tort des catégories réellement distinctes ?

Méthode de vérification retenue (après une fausse piste initiale, cf. détails ci-dessous) : pour chaque position de chiffre effectivement atteinte par la troncature niveau 4 (donc jamais au-delà du 5e chiffre, qui est de toute façon coupé avant même que la cascade s’exécute), on vérifie si “0” est en concurrence avec un chiffre non nul au même endroit, sous le même préfixe — c’est-à-dire si la cascade risque de fusionner une vraie sous-catégorie (un “1”, “2”, “3”… qui existe réellement à cette position) avec le cas “0”. Si “0” n’est jamais observé en concurrence avec une autre valeur à une position donnée, le retirer ne peut pas faire perdre d’information : il n’y avait rien d’autre à cette position pour ce préfixe.

(Une première tentative avait consisté à vérifier si “0” avait des “enfants” – un chiffre supplémentaire après lui – mais ces chiffres supplémentaires sont au-delà du 5e chiffre, donc hors du périmètre de la troncature niveau 4 : ce critère était incorrect et a été abandonné.)

charger_run <- function(objet_s3) {
  df <- aws.s3::s3read_using(
    FUN = arrow::read_parquet, object = objet_s3, bucket = bucket_s3,
    opts = list(region = "", base_url = endpoint_s3),
  )
  if (!"ligne" %in% names(df)) df$ligne <- seq_len(nrow(df)) - 1L
  df
}

tous_codes <- tous_codes[!is.na(tous_codes) & !tous_codes %in% c("AUCUNE_SUGGESTION", "NON_CODABLE")]

diviser_groupes <- function(code) {
  chiffres <- str_extract_all(code, "[0-9]")[[1]]
  if (length(chiffres) < 2) return(NULL)
  c(paste(chiffres[1:2], collapse = ""), chiffres[-(1:2)])
}

n_chiffres_cible <- niveau + 1  # 5

lignes_struct <- bind_rows(lapply(tous_codes, function(code) {
  g <- diviser_groupes(code)
  n <- length(g)
  if (n < 3) return(NULL)
  n_chiffres_cumules <- c(2, 2 + seq_len(max(0, n - 1)))
  positions_valides <- which(n_chiffres_cumules <= n_chiffres_cible & seq_along(g) >= 3)
  if (length(positions_valides) == 0) return(NULL)
  bind_rows(lapply(positions_valides, function(i) {
    data.frame(prefixe = paste(g[1:(i - 1)], collapse = "."), chiffre = g[i], stringsAsFactors = FALSE)
  }))
}))

bilan_positions <- lignes_struct %>%
  distinct(prefixe, chiffre) %>%
  group_by(prefixe) %>%
  summarise(valeurs = paste(sort(unique(chiffre)), collapse = ","), n_valeurs = n(), .groups = "drop")

positions_a_risque <- bilan_positions %>% filter(grepl("0", valeurs) & n_valeurs > 1)

Conclusion : aucune position à risque trouvée. Le “0” terminal ne sert jamais à distinguer une vraie sous-catégorie à un niveau atteint par la troncature niveau 4 — le fix cascade est légitime, pas une sur-correction. C’est cette conclusion que tronquer_niveau() (R et Python) applique partout sur ce site.

Depuis le run codif-x98xl (2026-07-30), une colonne code_lvl4 est calculée en amont du pipeline pour le vrai code, et correspond à 100 % à ce même fix cascade (vérification détaillée dans la synthèse SIRUS, qui l’utilise directement).
